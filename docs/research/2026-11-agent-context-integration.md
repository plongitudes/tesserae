# Keeping `tess` in a coding agent's context (Claude Code, November 2026)

Researched 2026-11-09. Primary sources are the Claude Code docs at code.claude.com (fetched that day as Markdown; none of the pages carry a date, and the newest Claude Code version they mention is v2.1.314), Anthropic engineering posts, the agents.md and agentskills.io specs, and source repos read through the GitHub API. Practitioner opinion is labelled as such. Token figures marked "est." are my own estimates at roughly 4 characters per token. They are not measured.

## Summary

Anthropic's current guidance points one way: if a system has a CLI, the agent should use the CLI and read `--help`. Claude Code's best-practices page names "your issue tracker" as its example ([best-practices](https://code.claude.com/docs/en/best-practices.md#connect-the-tools-claude-needs)), and the costs page says CLIs "are still more context-efficient than MCP servers because they don't add any per-tool listing" ([costs](https://code.claude.com/docs/en/costs.md#reduce-token-usage)). Standing context should be small, factual and conditional. CLAUDE.md should stay under 200 lines and hold only what Claude needs in every session ([memory](https://code.claude.com/docs/en/memory.md)). Procedures belong in skills, which cost only their description until they are used ([best-practices](https://code.claude.com/docs/en/best-practices.md#put-team-procedures-in-skills)). Hook-injected context should be "factual statements rather than imperative system instructions", because text framed as system commands "can trigger Claude's prompt-injection defenses" ([hooks](https://code.claude.com/docs/en/hooks.md#add-context-for-claude)). That last point is the main reason the `bd prime` style (a large, forceful always-on block) has aged badly.

Two findings affect the design beyond context:

1. **Cloud sessions load neither plugins nor user-level config.** A cloud session doesn't install plugins enabled in the repo's `.claude/settings.json` or in user settings, and doesn't read `~/.claude/`. It does load the repo's committed `CLAUDE.md`, `.claude/settings.json` hooks, `.claude/skills/`, `.claude/rules/` and `.mcp.json` ([cloud-environments](https://code.claude.com/docs/en/cloud-environments.md#what-carries-over-from-your-setup), [plugins/install](https://code.claude.com/docs/en/plugins/install.md)). Anything that has to work in the cloud must therefore be committed to the repo, or be a skill enabled on the claude.ai account.
2. **The cloud GitHub proxy looks like it will reject `tess sync`'s push.** The docs say: "the proxy rejects branch deletions and pushes of anything other than a branch, such as a tag" ([cloud-environments, GitHub proxy](https://code.claude.com/docs/en/cloud-environments.md#github-proxy)). ADR-0004 puts sync on `refs/tess/sync` and says it "works in cloud sessions". On the docs as written, a push to a non-branch ref would be refused. I haven't tested this; see Open questions.

### Recommended integration design

Ordered from most to least leverage. The CLI pieces cost no context until used and work in every agent, so they come first.

| # | Piece | What it contains | Where it lives | Context cost |
|---|---|---|---|---|
| 1 | **Agent-grade CLI** | Example-rich `--help` on every command; `--json` everywhere (already planned); stable error `code` plus a one-line remediation `hint` in the JSON error; flat output when not a TTY (already planned); `tess` with no args prints about 10 lines of orientation (commands for find work, record work, set status, comment, sync). | the binary | 0 standing; about 100-400 tokens (est.) per `--help` read |
| 2 | **Actor auto-detection** | If `TESS_ACTOR` is unset and `CLAUDECODE=1`, set `changed_by` to `claude:<first 8 of CLAUDE_CODE_SESSION_ID>`, or use `CLAUDE_CODE_REMOTE_SESSION_ID` in cloud sessions. Explicit `TESS_ACTOR` still wins. | the binary | 0 |
| 3 | **Contextual nudges on stderr** | Short factual lines only when relevant, for example `note: 3 local changes not yet synced (tess sync)` after a mutation when the last sync is old. Never on every command. | the binary | a few tokens, only when true |
| 4 | **One skill, `tess`** | Description of about 300 characters that says when to use it (track, find, record or update work items; "what should I work on"). The body is about 40-60 lines: the workflow loop (`tess ready`, then `tess status ID in-progress`, then work, then `tess create ... --blocked-by/discovered-from`, then `tess status ID done`/`pending-review`, then `tess comment`), JSON field notes, "run `tess sync` when you finish a unit of work", and pointers to `tess help <topic>`. `allowed-tools: Bash(tess *)` lets it run without prompts. Optionally a dynamic `` !`tess ready -n 5 \|\| true` `` line so the live queue arrives with the skill. | `.claude/skills/tess/SKILL.md` (committed) | about 80 tokens (est.) per request for the listing; about 600-900 tokens (est.) once invoked |
| 5 | **SessionStart hook** | `tess agent-hook session-start`: on `startup` (and `resume`, if more than N minutes have passed) run `tess sync` with a short timeout, then print 3-6 factual lines, for example `tess: 7 ready, 2 in progress (1 claimed by this session's actor), last synced 2 min ago`. On `compact`, skip the sync and print the same summary. Prints nothing if the repo has no tess database. | `.claude/settings.json` (committed) | about 60-150 tokens (est.) per session |
| 6 | **SessionEnd hook** | `tess agent-hook session-end`, which forks a detached `tess sync` and exits at once. The SessionEnd budget is 1.5 s, and timeouts set on plugin hooks don't raise it. | `.claude/settings.json` | 0 |
| 7 | **Generator** | `tess setup claude [--check\|--remove]` writes and updates items 4-6, plus a `permissions.allow` entry for `Bash(tess *)`, and checks that the hooks aren't installed twice. Its output is small and versioned with the binary. | the binary | 0 |
| 8 | **Cloud bootstrap** | Get `tess` onto the cloud VM: in the hook script, `if [ "$CLAUDE_CODE_REMOTE" = true ] && ! command -v tess; then go install …/cmd/tess@vX \|\| true; fi`, or the same line in the cloud environment's setup script, which is cached. Go and `proxy.golang.org` are available by default. | hook script or environment setup script | 0 |
| 9 | **Optional AGENTS.md line** | A single line for non-Claude agents: "Work items are tracked with `tess` (`tess --help`, `tess ready`)." | `AGENTS.md` | about 20 tokens (est.) |

Standing cost per session: about 150-250 tokens (est.), against the 1-2k tokens that beads' own docs give for `bd prime` ([beads docs](https://beads.gascity.com/integrations/claude-code.md)).

Things I would not do: an MCP server, UserPromptSubmit or Stop hooks, a PreCompact hook, an output style, a subagent, or a CLAUDE.md block. Reasons are in the sections below.

A Claude Code plugin is still worth publishing later as a second distribution for machines and repos where you don't want to commit `.claude/` files. It would bundle the same skill and hooks. It doesn't reach cloud sessions, and having both the plugin and the committed files in one repo would fire each hook twice. Beads ran into exactly this ([beads docs](https://beads.gascity.com/integrations/claude-code.md)).

## Mechanisms

### CLAUDE.md, AGENTS.md, rules, imports

- **Loading and cost.** CLAUDE.md loads in full at session start and is paid for on every request ([features-overview](https://code.claude.com/docs/en/features-overview.md#understand-context-costs)). The project-root CLAUDE.md is re-read from disk after compaction ([context-window](https://code.claude.com/docs/en/context-window.md#what-survives-compaction)).
- **Size and tone.** Target "under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Imports via `@path` (up to four hops deep) "don't reduce its context cost" ([memory](https://code.claude.com/docs/en/memory.md)). The docs say plainly that "adding IMPORTANT probably won't fix it". Either the file is too long, or the rule can't have exceptions and belongs in a hook ([best-practices](https://code.claude.com/docs/en/best-practices.md)). A one-line rule such as "always do X before you finish" in CLAUDE.md "works most of the time, not every time" (same page).
- **What belongs there.** "facts Claude should hold in every session". Multi-step procedures should move to a skill or a path-scoped rule ([memory](https://code.claude.com/docs/en/memory.md#when-to-add-to-claude-md)).
- **AGENTS.md.** Claude Code reads AGENTS.md natively from v2.1.277, but by default only when no `CLAUDE.md`/`.claude/CLAUDE.md`/`CLAUDE.local.md` exists in the working directory or above it. A setting (`claude-md-and-agents-md`) reads both, and a CLAUDE.md can also `@AGENTS.md` ([memory, AGENTS.md](https://code.claude.com/docs/en/memory.md#agents-md)). AGENTS.md itself is "a README for agents", is now stewarded by the Agentic AI Foundation under the Linux Foundation, and is read by Codex, Gemini CLI, Cursor, Copilot coding agent, Zed, Aider, Jules and others. The nearest file in the tree wins ([agents.md](https://agents.md/)).
- **`.claude/rules/` with `paths:`.** These load only when matching files are touched, and are then summarized away on compaction ([context-window](https://code.claude.com/docs/en/context-window.md)). They don't fit tess, because issue tracking isn't tied to file paths.
- **Relevance to tess.** At most one line, and preferably in AGENTS.md so every agent sees it. The skill description already advertises the tool to Claude.

### Skills

- **Progressive disclosure.** The name and description are always in context, and the body loads only when the skill is invoked ([skills](https://code.claude.com/docs/en/skills.md)). The open spec suggests about 100 tokens of metadata, under 5,000 tokens of body, and under 500 lines ([agentskills.io spec](https://agentskills.io/specification)). The idea comes from Anthropic's October 2025 post, and Agent Skills was published as an open standard on 2025-12-18 ([engineering post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)).
- **Descriptions.** `description` plus `when_to_use` is truncated at 1,536 characters in the listing; put the key use case first. The whole listing has a budget of 1% of the context window, and when it overflows Claude Code drops descriptions for some skills ([skills](https://code.claude.com/docs/en/skills.md)). The spec caps `description` at 1,024 characters ([spec](https://agentskills.io/specification)). If you want portability, stay under 1,024.
- **Lifecycle.** Once a skill is loaded it stays in context and isn't re-read. After compaction it is re-attached, capped at 5,000 tokens per skill and 25,000 tokens in total, oldest first to go, with truncation keeping the start of the file ([context-window](https://code.claude.com/docs/en/context-window.md)). So the critical lines go at the top of SKILL.md. The docs also advise "write standing instructions" and "each line in a loaded skill is a recurring token cost" ([skills](https://code.claude.com/docs/en/skills.md)).
- **Useful features for tess.** Dynamic injection with `` !`cmd` `` runs before the skill is sent to Claude. A failing command aborts the whole invocation, so append `|| true`, and the command must match an allow rule or `allowed-tools`. `allowed-tools: Bash(tess *)` pre-approves tess for the invoking turn. `${CLAUDE_SESSION_ID}` substitution is available. Frontmatter `hooks:` are registered when the skill is invoked and stay for the rest of the session ([skills](https://code.claude.com/docs/en/skills.md), [hooks, hooks in skills](https://code.claude.com/docs/en/hooks.md#hooks-in-skills-and-agents)). That makes it possible to register a SessionEnd sync only in sessions that actually used tess. I haven't verified that SessionEnd is honoured from skill frontmatter.
- **Where skills load.** `~/.claude/skills` is local only. `.claude/skills` in the repo works locally, in worktrees (which fall back to the main checkout's project skills from v2.1.277) and in cloud sessions, but not in project cloud threads. Skills enabled on the claude.ai account load in cloud sessions, Cowork, and signed-in terminals. Commands in synced skills aren't executed on the local machine ([skills](https://code.claude.com/docs/en/skills.md#use-skills-in-cowork-and-cloud-sessions)).
- **Testing.** Compare against a baseline in fresh sessions; `/skill-doctor` finds skills that cost context but never fire, and `claude plugin eval` covers plugin skills ([skills](https://code.claude.com/docs/en/skills.md)).
- **Slash commands** have merged into skills: `.claude/commands/x.md` and `.claude/skills/x/SKILL.md` both create `/x` ([skills](https://code.claude.com/docs/en/skills.md)). Separate `/tess-ready` style commands add little over the skill and the CLI. `disable-model-invocation: true` keeps a user-only command out of context entirely if you want one.

### Plugins and marketplaces

- **What a plugin can bundle.** Skills, commands, agents, hooks, MCP servers, LSP servers, output styles, workflows, themes and monitors (both experimental), `settings.json` (only `agent` and `subagentStatusLine` take effect), `userConfig`, and a `bin/` directory that goes on the Bash tool's `PATH` while the plugin is enabled. A plugin can't ship permission rules. A `CLAUDE.md` at the plugin root isn't loaded ([plugins-reference](https://code.claude.com/docs/en/plugins-reference.md)).
- **`bin/` caveat.** "claude.ai and Cowork don't install a plugin that has a top-level `bin/` directory" ([plugins-reference](https://code.claude.com/docs/en/plugins-reference.md), [components](https://code.claude.com/docs/en/plugins/components.md)). It would also put a second `tess` binary beside the user's own install. Use it only if the plugin is the distribution channel.
- **Install scopes.** User (`~/.claude/settings.json`), project (`.claude/settings.json`, committed, but every collaborator must still run `claude plugin install … --scope project` once per clone), and local ([plugins/install](https://code.claude.com/docs/en/plugins/install.md#choose-an-install-scope)).
- **Updates.** Marketplaces with auto-update on refresh after a random delay of up to 10 minutes from the first message. The running session keeps the old version until `/reload-plugins`. Setting `version` pins users until you bump it ([plugins/loading](https://code.claude.com/docs/en/plugins/loading.md#versions-and-updates)).
- **Cloud sessions.** "has no plugin browser and doesn't load the plugins you installed on your own machine or the ones your repository's `.claude/settings.json` turns on" ([plugins/install](https://code.claude.com/docs/en/plugins/install.md)). Plugins enabled on a claude.ai account sync to terminal and Cowork sessions ([plugins/loading](https://code.claude.com/docs/en/plugins/loading.md#synced-plugins)). The docs don't say synced plugins load in Claude Code cloud sessions (unverified either way).
- **Cost.** Packaging adds no context cost of its own; each bundled component costs what it would cost on its own ([features-overview](https://code.claude.com/docs/en/features-overview.md)).
- **Relevance to tess.** A plugin is good for one-time per-machine installs and updates, but it can't be the only channel while cloud sessions matter.

### Hooks

Events (33 in the current list) include SessionStart, SessionEnd, Stop, PreCompact/PostCompact, UserPromptSubmit, CwdChanged, WorktreeCreate/Remove and others ([hooks](https://code.claude.com/docs/en/hooks.md)).

- **SessionStart.** Matchers are `startup`, `resume`, `clear`, `compact` and `fork`. Plain stdout, or `hookSpecificOutput.additionalContext`, becomes a system reminder at the start of the conversation. At launch the hook runs in the background, and the first response waits for it. Only `command` and `mcp_tool` types run, and `mcp_tool` is skipped at launch. "SessionStart runs on every session, so keep these hooks fast." Default timeout is 600 s. The hook can also set `sessionTitle`, `watchPaths` and `reloadSkills` ([hooks, SessionStart](https://code.claude.com/docs/en/hooks.md#sessionstart)).
- **Output limits.** `additionalContext` and plain stdout are capped at 10,000 characters; anything longer goes to a file, and Claude gets only a 2,000-character preview ([hooks](https://code.claude.com/docs/en/hooks.md#add-context-for-claude)).
- **Tone.** Use factual statements ("The deployment target is production"), not out-of-band commands, or Claude may surface the text to the user as a possible injection (same section).
- **Compaction.** Context that hooks added earlier is summarized along with the conversation. Only SessionStart hooks that match `compact` re-add it ([context-window](https://code.claude.com/docs/en/context-window.md#what-survives-compaction)). The tess SessionStart hook should match `compact` too, but skip the network sync there.
- **Persisting environment variables.** SessionStart (also Setup, CwdChanged, FileChanged) gets `CLAUDE_ENV_FILE`; `export` lines appended to it persist into later Bash commands ([hooks, persist env vars](https://code.claude.com/docs/en/hooks.md#persist-environment-variables)). It isn't needed for the actor, because Claude Code already sets `CLAUDE_CODE_SESSION_ID` in every Bash tool subprocess, and that matches the hook's `session_id` and updates on `/clear`. It also sets `CLAUDECODE=1`, and in cloud sessions `CLAUDE_CODE_REMOTE=true` and `CLAUDE_CODE_REMOTE_SESSION_ID` ([env-vars](https://code.claude.com/docs/en/env-vars.md)). So `tess` can work out its own actor without a hook, which also works for agents that don't run hooks. Note that ADR-0013 says "The Claude Code plugin sets an agent identity"; this approach moves that into the binary.
- **SessionEnd.** Reasons are `clear`, `resume`, `logout`, `prompt_input_exit` and `other`. It can't block, and its output is discarded. "SessionEnd hooks have a default timeout of 1.5 seconds." A per-hook `timeout` in settings files raises the budget up to 60 s, but "Timeouts set on plugin-provided hooks don't raise the budget". `CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` overrides it ([hooks, SessionEnd](https://code.claude.com/docs/en/hooks.md#sessionend)). A sync that takes 0.5-2 s (ADR-0012's own estimate) won't reliably fit, so fork a detached process. The docs suggest the same for async work that must outlive `-p`: "start a fully detached process from it" ([hooks, async](https://code.claude.com/docs/en/hooks.md#run-hooks-in-the-background)). Whether SessionEnd fires at all when a cloud VM is reclaimed after idling isn't documented (unverified). Treat it as best effort, and keep "sync when you finish" in the skill as the main path.
- **Stop.** Fires every time Claude finishes a response. Exit 2 or `decision` keeps Claude going ([hooks, Stop](https://code.claude.com/docs/en/hooks.md#stop)). That's too frequent for sync or reminders. It enforces checks (tests) well, but it would turn tess into a nag.
- **PreCompact.** Its stdout becomes "instructions for the compaction summary" (truncated at 10,000 characters), not context ([hooks, PreCompact](https://code.claude.com/docs/en/hooks.md#precompact)). The beads plugin runs `bd prime` on both SessionStart (matcher `""`, which already includes `compact`) and PreCompact ([beads plugin.json](https://github.com/gastownhall/beads/blob/main/plugins/beads/.claude-plugin/plugin.json)). Used that way, the PreCompact output steers the summarizer rather than briefing Claude. It is probably redundant.
- **UserPromptSubmit.** Adds context on every prompt, and its timeout is lowered to 30 s ([hooks](https://code.claude.com/docs/en/hooks.md#userpromptsubmit)). That's a recurring cost with little value for tess.
- **General.** Exit 2 blocks (where the event can block); any other non-zero exit is a non-blocking error shown in the transcript. A timed-out hook's output is discarded. `async: true` runs the hook in the background and delivers its output on the next turn. In interactive sessions hooks wait for workspace trust. Hooks from settings files and plugins also run inside subagents. Subagent hooks receive `agent_id`, but there is no subagent ID in the Bash environment ([hooks](https://code.claude.com/docs/en/hooks.md), [env-vars](https://code.claude.com/docs/en/env-vars.md)).
- **Worktrees.** The hook `cwd` follows Claude into worktrees, while `CLAUDE_PROJECT_DIR` stays at the session's starting root ([hooks](https://code.claude.com/docs/en/hooks.md#common-input-fields)). That works with ADR-0003's single database in the git common dir.

### Cloud (claude.ai/code) sessions

- Each session gets a fresh Ubuntu 24.04 x86_64 VM with a fresh clone. Go, git, gh and jq are preinstalled, and `proxy.golang.org` and `release-assets.githubusercontent.com` are on the default allowlist ([cloud-environments](https://code.claude.com/docs/en/cloud-environments.md#installed-tools)).
- Setup scripts run as root before Claude Code starts and are cached as a filesystem snapshot if they finish in about 5 minutes. They run only in the cloud. SessionStart hooks run in both places, and the docs' own pattern guards cloud-only installs with `CLAUDE_CODE_REMOTE` ([cloud-environments, setup scripts vs hooks](https://code.claude.com/docs/en/cloud-environments.md#setup-scripts-vs-sessionstart-hooks)).
- Sessions with several repositories, and threads inside a project, don't run repo hooks at all (same page, "Limitations in cloud sessions").
- The GitHub proxy rejects pushes of anything other than a branch, and it rejects GraphQL, which means `gh issue` and `gh pr` don't work there ([cloud-environments, GitHub proxy](https://code.claude.com/docs/en/cloud-environments.md#github-proxy)). This bears directly on `refs/tess/sync`.

### MCP server vs. a CLI called through Bash

- **Anthropic's position.** Use a CLI when one exists ([best-practices](https://code.claude.com/docs/en/best-practices.md#connect-the-tools-claude-needs), [costs](https://code.claude.com/docs/en/costs.md#reduce-token-usage)). MCP is for systems that have no CLI and need connections or auth handled by a server ([features-overview](https://code.claude.com/docs/en/features-overview.md)).
- **Token cost today.** Tool search is on by default. At startup only tool names and server instructions load, and schemas are deferred. Server instructions are cut at 4,096 characters, and descriptions of deferred tools at 16,384. MCP output is capped at 25,000 tokens by default ([mcp, tool search](https://code.claude.com/docs/en/mcp.md#scale-with-mcp-tool-search)). So the old objection ("MCP schemas add 10-50k tokens to every request", as the beads docs put it) is mostly out of date for Claude Code. MCP still costs a little standing context and a server process, and it can't be piped through `jq` or grep.
- **The November 2025 "Code execution with MCP" post** argues that loading tool definitions up front and routing intermediate results through the model wastes context (150,000 down to 2,000 tokens in its example). It recommends presenting tools as code or files that the agent discovers on demand ([engineering post, 2025-11-04](https://www.anthropic.com/engineering/code-execution-with-mcp)). A CLI with good `--help` is already that shape.
- **Relevance to tess.** No MCP. Every target environment has a shell and a local binary. MCP would only make sense for a shell-less client such as Claude Desktop chat, and in that case it should share the CLI's domain layer. Arcjet, a practitioner source, argues the same: "Keep CLI and MCP as peer clients" ([Arcjet, 2026-06-02](https://arcjet.com/blog/designing-a-cli-for-ai-agents)).

### Subagents, output styles, monitors

- **Output styles** load on every request and change the system prompt ([features-overview](https://code.claude.com/docs/en/features-overview.md)). They are the wrong tool for this.
- **Subagents** get an isolated context ([features-overview](https://code.claude.com/docs/en/features-overview.md)). A "triage the backlog" agent is conceivable, but tess commands are cheap and need no isolation. Built-in Explore and Plan agents start without CLAUDE.md, but they can still invoke skills.
- **Plugin monitors** (experimental) run persistent background commands ([plugins-reference](https://code.claude.com/docs/en/plugins-reference.md)). Nothing in tess needs to be watched.

### CLI design for agents

- **Anthropic, on tool design** ([writing tools for agents, 2025-09-11](https://www.anthropic.com/engineering/writing-tools-for-agents)):
  - Build consolidated, workflow-shaped tools rather than one per endpoint.
  - Return high-signal, human-readable identifiers rather than UUIDs.
  - Offer concise vs. detailed response modes (about a third of the tokens in their example).
  - Paginate and truncate, with defaults that point the agent toward narrower queries.
  - Write error messages that state "specific, actionable" fixes rather than "opaque error codes or tracebacks".
  - Use unambiguous parameter names.
  - Iterate against evals.
- **Anthropic, on context engineering** ([effective context engineering, 2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). It recommends just-in-time retrieval through lightweight identifiers over pre-loading, and explicitly describes an agent keeping structured notes or a to-do list outside the context window as a memory pattern for long tasks. An issue tracker is that pattern made durable. It also warns that "bloated tool sets" with overlapping choices are a common failure mode. That supports ADR-0018's "one obvious way".
- **Claude Code docs.** "For a CLI it hasn't seen before, pointing it at `--help` is enough" ([best-practices](https://code.claude.com/docs/en/best-practices.md#connect-the-tools-claude-needs)).
- **Practitioners** (secondary sources):
  - Speakeasy ([2026-02-05](https://www.speakeasy.com/blog/engineering-agent-friendly-cli)): non-interactive mode, `--output json`, quiet mode with no spinners, distinct exit codes, help that reveals the command tree step by step, and "focused skills outperform comprehensive ones".
  - Arcjet ([2026-06-02](https://arcjet.com/blog/designing-a-cli-for-ai-agents)): treat commands, flags and JSON fields as a contract (additive changes only), no fuzzy "did you mean" corrections, structured JSON errors on stderr with remediation, TTY-based switching between text and JSON, `--fields` to trim output, realistic examples in help, and an env-var override for identity and auth.
- **Gaps against the tess draft** (`docs/design/cli.md` already has `--json`, stable error codes, stderr errors, non-TTY flat output):
  - a `hint` field in the JSON error;
  - examples in every `--help`;
  - a no-args orientation screen;
  - perhaps `--fields` or a compact JSON mode for `list`;
  - no fuzzy command correction;
  - idempotent status transitions (setting the status an issue already has succeeds as a no-op), so retries are safe.

## Other tools' practice

- **beads (`bd`).** It now ships a Claude Code plugin (v1.3.4) with one large skill, about 30 slash commands, a task agent, and `bd prime` on SessionStart and PreCompact. It also has Codex and Copilot plugin manifests ([repo tree](https://github.com/gastownhall/beads/tree/main/plugins/beads)). `bd setup claude` writes a SessionStart hook plus a CLAUDE.md pointer, and skips the hooks when the plugin is enabled so it doesn't prime twice. Its docs size the prime at about 1-2k tokens and recommend CLI plus hooks over MCP ([beads docs](https://beads.gascity.com/integrations/claude-code.md)). It is a useful contrast: the same pieces as recommended here, at five to ten times the standing size, with imperative tone and overlapping channels.
- **Official plugin directory.** In [`anthropics/claude-plugins-official`](https://github.com/anthropics/claude-plugins-official) (last commit 2026-11-10 UTC), the `linear`, `github` and `gitlab` external plugins each contain only a `plugin.json` and `.mcp.json`, which makes them thin MCP wrappers for hosted services. `asana` adds a setup command. Hosted SaaS trackers integrate through MCP, which fits Anthropic's rule, since they have no local CLI the agent is assumed to have.
- **GitHub CLI.** `gh` is the docs' example of a CLI Claude uses "without any explanation from you" ([best-practices](https://code.claude.com/docs/en/best-practices.md)). Since v2.90.0 (April 2026, preview) it also has `gh skill install/update/publish`, which installs Agent Skills into Claude Code, Codex, Cursor, Gemini CLI, Copilot and Antigravity, with `--pin` to lock a version ([GitHub changelog, 2026-04-16](https://github.blog/changelog/2026-04-16-manage-agent-skills-with-github-cli/)). That suggests tess's skill could also be published as a standalone Agent Skill in its repo, installable without the plugin system.
- **Backlog.md** (secondary sources, from a search summary of its README; not read directly). Its init wizard offers either MCP, recommended and auto-configured for Claude Code, Codex, Gemini CLI, Cursor and others, or CLI plus generated instruction files (CLAUDE.md, AGENTS.md, GEMINI.md). `backlog agents --update-instructions` refreshes those files ([GitHub](https://github.com/MrLesk/Backlog.md)). It is another example of a tool that writes and maintains its own instruction files.
- **Agent Skills and AGENTS.md as cross-agent standards.** Skills follow agentskills.io; AGENTS.md is read by most non-Claude agents ([agents.md](https://agents.md/)). A tess skill that keeps to the spec's frontmatter (`name`, `description` up to 1,024 characters, `allowed-tools`) will load in other agents. Claude-only keys such as `when_to_use` and `hooks` cause a hard error on claude.ai uploads and the Skills API ([skills](https://code.claude.com/docs/en/skills.md)), so keep them out of any copy meant for those surfaces.

## Open questions

1. **Cloud push of `refs/tess/sync`.** The docs say the proxy rejects pushes of non-branches, which contradicts ADR-0004's "works in cloud sessions". It needs a spike: from a cloud session, `git push origin HEAD:refs/tess/sync` and `git fetch origin refs/tess/sync`. If the push is rejected, the alternatives are a never-checked-out branch such as `refs/heads/tess/sync`, which brings branch-list noise, CI triggered on push, and possible PR suggestions, or accepting that cloud sessions are read-only for tess. Whether fetching a non-branch ref works through the proxy is also undocumented.
2. **SessionEnd in the cloud and from skill frontmatter.** Neither is documented. Test whether a detached `tess sync` survives session end, both locally and in the cloud.
3. **Actor granularity.** `CLAUDE_CODE_SESSION_ID` changes on `/clear` and is shared by subagents. There is no subagent ID in the Bash environment. Parallel agents in separate sessions or worktrees get separate IDs, which is probably the granularity you want. Decide whether `claude:<session8>` or `claude:<model>:<session8>` is the right shape.
4. **Committed files vs. plugin.** Committed `.claude/` files are needed for the cloud but are per-repo. Decide whether `tess init` should offer `tess setup claude` or leave it explicit, and whether to also publish a plugin (and a `gh skill` package). A plugin also needs a guard against double hooks, for example the hook script exiting if another tess hook already ran this session.
5. **Getting the binary onto cloud VMs.** If the tesserae module is private, `go install` through the proxy needs GitHub auth. A release asset download, or a setup script per cloud environment, may be simpler. Not tested.
6. **Measure.** Run `/context` with the skill and hook installed to replace the estimates in this note, and evaluate the skill's triggering against a no-skill baseline as the skills page recommends.
