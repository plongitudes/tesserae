# Loop 2 plan: sync

The ordered work list for the second build loop ([build plan](../../docs/design/build-plan.md), [sync.md](../../docs/design/sync.md)). One item per iteration, in order; the loop checks items off and the host stops when every item is checked and `scripts/ralph/check.sh --strict` passes. Each item names the docs that define it and what "done" means. The docs are the spec; this file only orders the work. Loop 1's plan and notes are in [plan-loop1.md](plan-loop1.md).

Package layout, from [module-map.md](../../docs/design/module-map.md): `internal/git` (runs the git binary), `internal/sync` (snapshot, merge, store, `Run`; the exported API in `sync.go` is fixed by [acceptance/README.md](../../acceptance/README.md) "The simulator"), `internal/sync/gitref` (the transport, the only place that knows ref names), and `internal/cli` for `sync`, `doctor` and the hooks.

## Items

- [x] 1. Git plumbing. `internal/git`: run the user's `git` binary for what the transport needs ([sync.md](../../docs/design/sync.md) "Git", [ADR-0020](../../docs/adr/0020-v1-dependencies.md)): `rev-parse` (common dir, a ref's commit, whether a ref exists), the remotes and their URLs, `fetch` of one refspec into a local ref, `push` with `--force-with-lease=<ref>:<expected>`, `update-ref` with the expected old value, `ls-tree -r` of a commit, `cat-file --batch` for many blobs in one process, and writing a whole tree and commit in one process (`fast-import`, or `hash-object --stdin-paths`/`mktree`/`commit-tree` if fast-import proves awkward; say which in the notes). Author, committer and dates come from arguments, never from the environment. Errors are classified: the remote unreachable (`offline`), a non-fast-forward rejection (retryable), any other rejection (`push_rejected` with git's reason), with the stable codes as `*tracker.Error`. Move the `rev-parse` helpers of `internal/cli/env.go` here and make `cli` call them. Done when unit tests against bare repositories under `$TMPDIR` cover each operation, a rejected push from a `pre-receive` hook, a non-fast-forward push after the remote moved, and an unreachable remote path.
- [x] 2. Snapshot. `internal/sync`: the `Snapshot` types as exported, `Files()` with the canonical encoding of [sync.md](../../docs/design/sync.md) "The snapshot" (key order, no whitespace, one trailing newline, RFC 3339 UTC seconds, texts by hash with bodies under `texts/`, each link on the issue whose event log records it, `related` on the smaller ID, collections sorted, `config.json` with `format` and `prefix`), a `FromFiles` that parses the tree back, and `Load` from a database (stored status, never `waiting`; every issue including retired ones; all comments, events and texts). Done when unit tests show `Files()` → `FromFiles` → `Files()` is the identity, two databases that reach the same state by different operation orders give identical files, and `Load` of a database built through the tracker holds what the tracker shows.
- [ ] 3. Done when unit tests cover every rule in that section with snapshots built in memory, including change-and-change-back, remove-then-add of a label, an edit after and before a retire, no-event fallbacks, and symmetry (`Merge(l, a, b)` and `Merge(l, b, a)` give identical files and the same resolutions with `won` flipped).
- [ ] 4. Structure after the merge. ## Notes

Iterations append here, newest at the bottom, under a heading `### Item N`. Human-facing: decisions, deviations, gotchas, what to look at by hand.

### Item 1

- `internal/git` is `git.Repo{Dir}` (empty `Dir` is the working directory) with one method per operation, each one git process: `CommonDir`, `WorktreeRoot`, `ResolveRef`, `Remotes`, `UpdateRef` (git.go); `WriteCommit`, `ListTree`, `ReadBlobs`, and the in-process `BlobHash` (objects.go); `Fetch`, `Push` (remote.go). The package knows no ref names; every ref is an argument.
- Writing is `fast-import`, one process for blobs, trees and the commit. fast-import insists on a branch name for a commit and would write that ref at the end, so the stream names a scratch branch (`refs/fast-import/scratch`), then `reset`s it with no commit, which leaves fast-import nothing to write; the commit's ID comes back through `get-mark`. A test asserts no ref exists afterwards. `--done` makes a truncated stream an error.
- `Commit.Files` and `Commit.Delete` are changes against the first parent's tree (fast-import's `from` semantics; empty tree with no parents). Item 6 should put the commit it diffs against first in `Parents` and send only the files whose `BlobHash` differs from `ListTree` of that parent.
- Identity and dates are written into the stream from `Signature{Name, Email, When}`, always `+0000`; a test sets every `GIT_AUTHOR_*`/`GIT_COMMITTER_*` variable and checks none reaches the commit. `<`, `>` and newlines are dropped from a name, as git drops them.
- Push classification reads `push --porcelain`: a `!` line for the ref with `[rejected] (stale info | fetch first | non-fast-forward)` is `git.ErrRemoteMoved` (a sentinel, not a `*tracker.Error`: the transport retries and decides when it becomes `push_rejected`); any other `!` line is `push_rejected` carrying git's reason plus the remote's `remote:` lines; a failed push with no `!` line is `offline`. With `--force-with-lease` a moved remote reads `stale info`, not `non-fast-forward`; that is the case the test covers.
- `Fetch` returns `(found, err)`: a remote without the ref is `false, nil` (read from git's "couldn't find remote ref", which is why every git process runs with `LC_ALL=C`) and leaves the destination ref as it was; any other failure is `offline` with git's first `fatal:` line in the message. A context that ended comes back as the context's error, not `offline`, so item 10's deadline can be told apart.
- `Push` passes `--no-verify`, so the user's own `pre-push` hook (their test run, say) doesn't fire on a sync, and `--no-follow-tags`/`--no-recurse-submodules`; `Fetch` passes `--no-tags --no-write-fetch-head --no-recurse-submodules`. None of this is in sync.md; say if any of it should not be there.
- `cli/env.go` now calls `git.Repo{}.CommonDir` and `WorktreeRoot`; `not_a_git_repo` is `git.CodeNotAGitRepo`, and the "not inside a working tree" case is `git.ErrNoWorktree`, mapped to `invalid_argument` in `cli` as before. No deviations from the docs.

### Item 2

- `internal/sync/snapshot.go` holds `Files()` and `FromFiles(files map[string][]byte) (*Snapshot, error)`; `internal/sync/load.go` holds `Load`. The key order is the declaration order of four unexported file structs (`configFile`, `issueFile`, `commentFile`, `eventFile`) written with `encoding/json`, HTML escaping off, so `<`, `>` and `&` appear as themselves. New exported names beside the fixed API: `FromFiles`, `Format` (1) and `CodeFormatUnsupported`.
- `Files()` sorts copies of the collections and never changes the snapshot; a nil collection is written `[]`. It writes `related` as the snapshot holds it: putting it on the smaller ID is done by whoever builds the snapshot (`Load` here, `Merge` in item 3).
- `FromFiles` is strict: a path outside the five kinds, a key it does not know, a second JSON value in a file, an ID or issue ID that does not match the path, or a text whose bytes do not hash to its name is an error. Rewriting a snapshot would silently lose anything it skipped. It reads only `format` from `config.json` first and returns `format_unsupported` (a `*tracker.Error`, hint to upgrade) before parsing anything else, so a later format is free to reshape every file. The other failures are plain errors with no stable code.
- `Load` reads the `issues`, `labels`, `links`, `comments`, `events` and `texts` tables directly, in one read transaction, not through `live_issues` or `issue_states`: the stored status, retired issues, and links to and from retired issues (a child keeps its `parent` in the snapshot while the tracker shows none because the parent is retired). Which issue holds a link comes from `sqlite.LinkOwner`, the function the store logs link events with, after turning a `related` row so the smaller ID is first.
- Timestamps are cut (not rounded) to the second in `Load` and in `FromFiles`, so a snapshot in memory equals its files. The database keeps milliseconds.
- Event values are the plain JSON values in both `Load` and `FromFiles`: `nil`, `string`, `float64` (a priority event is `float64(1)`, not `int`), matching what the README says of `Resolution.Kept`/`Dropped`.
- `Load` of a missing or uninitialised database is `not_initialized` and creates no file, as `tracker.Open` does. The message is a copy of the tracker's, whose constructor is unexported.
- No deviations from the docs.

### Discovered

(Work found outside the current item: one line each, for the human to turn into items or issues.)

- `cli/env.go` `actor` still runs `git config user.name` itself; item 1 moved only the `rev-parse` helpers it named. It could become `git.Repo.UserName` so `internal/git` is the only place that starts git.
- `internal/git` assumes SHA-1 object IDs in `BlobHash` (sync.md says SHA-1). A repository created with `--object-format=sha256` would see every blob as changed; `tess doctor` could say so.
- `internal/sync` repeats the `not_initialized` error text of `tracker/open.go` in `load.go`; exporting the tracker's constructor would leave one copy.

### Reflections

(Candid notes on the docs, the suite, and the process, per item.)

- Item 1: a failed push or fetch that never reached a per-ref answer is reported as `offline`, whatever the cause. That is right for an unreachable remote and for failed authentication, but a local failure (a corrupt object, a full disk) would read as `offline` too. Git's own first `fatal:` line is in the message, so the user sees the real reason; I did not try to tell these apart by matching more of git's wording.
- Item 1: I also treat a `[remote rejected]` whose reason starts `failed to update ref` or `failed to lock` as `ErrRemoteMoved`: it is what the remote says when another push lands between its advertisement and our update. I could not produce that race in a test, so that branch is untested; if the reason is really a permanent one (permissions on the remote's ref), the cost is two wasted retries before `push_rejected`.
- Item 1: the item says "a non-fast-forward push after the remote moved", but with `--force-with-lease` git never reports `non-fast-forward` for this; it reports `stale info`. I took the item to mean the situation, not the word, and accept all three of git's wordings.
- Item 1: git prompts are left alone (no `GIT_TERMINAL_PROMPT=0`). A remote that asks for a password would hang the session-start hook until its ten-second deadline; item 10 may want prompts off for the hook only.
- Item 2: item 5 should know that the snapshot is to the second and the database to the millisecond. Writing a merged issue back replaces `updated_at`, `created_at` and event `changed_at` with whole seconds; that is harmless for the merge (event order falls back to the event ID, a ULID that keeps its milliseconds), but a row the sync rewrites loses its milliseconds, and `list` orders by `created_at`. Item 5 could keep the stored value where the second matches.
- Item 2: "two databases that reach the same state by different operation orders give identical files" cannot hold for the whole tree once an operation logs an event or a comment, since those IDs are random ULIDs. I tested it in two parts: a creation-only build in two orders (labels and blockers given in different orders) compared file for file, and edits in different orders at one clock time compared on everything but `events/`.
- Item 2: a `related` link given in opposite wordings gives the same `related` list but not the same issue files: the tracker logs the link, and moves `updated_at`, on the issue it was given from, so the two copies differ in `updated_at` on both endpoints until a merge takes the later one. sync.md's "produce the same file" is true of the link, not of the whole file. My first version of the test asserted the whole file and failed on this; the test now uses one wording there and a separate test covers the opposite wordings.
- Item 2: strictness in `FromFiles` is my call, not the docs'. The cost is that a stray file on the ref (someone commits a README to `refs/tess/sync` by hand) fails every sync with an uncoded error until it is removed. If a later item wants that to be a code, `doctor` or `Run` is the place.
