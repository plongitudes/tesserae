# Loop 1 plan: the core

The ordered work list for the first build loop ([build plan](../../docs/design/build-plan.md)). One item per iteration, in order; the loop checks items off and the host stops when every item is checked and `scripts/ralph/check.sh --strict` passes. Each item names the docs that define it and what "done" means. The docs are the spec; this file only orders the work.

Package layout, from [module-map.md](../../docs/design/module-map.md): `cmd/tess` (just `os.Exit(cli.Main())`), `internal/cli` (adapter: cobra commands, flags, JSON and human output), `internal/tracker` (all behaviour, the `Tracker` interface), `internal/ids` (pure), `internal/store/sqlite` (schema, views, transactions, events). No `sync` package in loop 1.

## Items

- [x] 1. SQLite store: schema, views, transactions. `internal/store/sqlite`. Open or create the database file named in [cli.md](../../docs/design/cli.md) (`init`), WAL mode, `BEGIN IMMEDIATE` with busy retry ([ADR-0003](../../docs/adr/0003-global-issues-in-git-common-dir.md), [ADR-0006](../../docs/adr/0006-ncruces-sqlite-driver.md); don't import the driver's `embed` package). Tables: `issues` (texts held as hashes), `texts(hash, body)` ([ADR-0014](../../docs/adr/0014-content-addressed-text.md)), `labels`, `links` (one row per link, canonical direction, [ADR-0015](../../docs/adr/0015-four-link-types.md)), `comments`, `events` ([ADR-0013](../../docs/adr/0013-field-level-event-log.md)), `config` (prefix, schema version). Views: `live_issues` ([ADR-0010](../../docs/adr/0010-retire-instead-of-delete.md)), readiness edges, `blocked_issues` ([ADR-0007](../../docs/adr/0007-readiness-is-one-sql-view.md), [ADR-0016](../../docs/adr/0016-hierarchy-rules.md); recursion guard ~100), and a view or query for "has open children". Done when unit tests against `:memory:` cover: a direct active blocker; a `done`/`omit`/retired blocker not blocking; a blocked ancestor and a `held` ancestor blocking a grandchild; open children not making the parent blocked; and two connections writing concurrently without a `SQLITE_BUSY` surfacing.
- [x] 2. IDs. `internal/ids`: generate `<prefix>-<base36>` from a SHA-256 over prefix, title, creator, created_at and a nonce, with the length adaptive to the issue count and at least 3 characters ([ADR-0017](../../docs/adr/0017-flat-immutable-ids.md); the old tool's `internal/idgen/hash.go` and `adaptive_length.go` are the reference); collision handling inside the create transaction. Resolution rules as pure logic over candidates the store supplies: exact, then unique prefix, then unique substring, never matching retired issues, `ambiguous_id` listing the candidates, `not_found` otherwise ([requirements.md](../../docs/requirements.md), [README](../../acceptance/README.md) "Retired issues" and "ID shape"). Imported IDs like `bd-abc.1` must still resolve exactly. Done when unit tests cover generation shape, adaptive length, collision, and every resolution rule.
- [x] 3. Tracker: create, get, update. `internal/tracker` with the `Tracker` interface from the module map, a clock and an actor passed in (no globals). `Create` allocates the ID in the transaction, stores texts by hash, labels, `--parent` and `--blocked-by` links. `Get` resolves a partial ID and returns the full issue object of the [README](../../acceptance/README.md): displayed status (`waiting` for a stored `ready` that is blocked or has open children), `blocked`, `ancestors` nearest first, sorted `labels`, `links.*` omitting retired issues, `comments`, `previous_status` for a held issue (from events), and `history` on request. `Update` takes a typed `Patch`; the store diffs it into events in the same transaction (only changed fields; `updated_at` never; text fields log hashes; labels one element per event); clearing optional fields; `retired` refused. ## Notes

Iterations append here, newest at the bottom, under a heading `### Item N`. Human-facing: decisions, deviations, gotchas, what to look at by hand.

### Item 1

- `internal/store/sqlite`: `Open(ctx, path)` creates the file and schema if absent (`:memory:` works), `Write`/`Read` run a function in a transaction over `*sql.Tx`, plus `Config`/`SetConfig`. The schema is one embedded file, `schema.sql`; `config.schema_version` is `1` and `Open` refuses any other version. `Open` does not set the prefix: `init` (item 7) writes `config.prefix` with `SetConfig`, and decides `not_initialized`/`already_initialized` by whether the file exists before calling `Open`.
- Connection setup is a driver init callback, not DSN parameters: busy timeout 5 s, then `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`. One connection per store (`SetMaxOpenConns(1)`), which is also what keeps `:memory:` to a single database. `Write` begins with `sql.LevelSerializable`, which the driver maps to `BEGIN IMMEDIATE`, and retries a busy `BEGIN` with backoff for up to 30 s.
- Text columns on `issues` (`description`, `design`, `acceptance_criteria`, `notes`) always hold a hash, never NULL: the empty text's row is seeded in `texts` and is the column default. So the first edit of a description logs the SHA-256 of the empty string as `old_value`, not `null`.
- Links: one row `(from_id, type, to_id)` in the canonical direction of the acceptance README. The schema itself refuses a second parent, a self-link, an unknown type, and a `related` link given the other way round (unique index on `min(from,to), max(from,to)`). The tracker still has to check these first to give `has_parent`/`cycle` instead of a constraint error. `related` is stored as given, so reading "related to X" means looking at both columns.
- Views: `live_issues`, `readiness_edges(type, from_id, to_id)` (blocks and parent links between live issues), `blocked_issues(id)`, `issue_ancestors(id, ancestor_id, depth)` (depth 1 = parent; use it for `ancestors` and for `list --parent`), `open_children(parent_id, id)` (all open descendants, per ADR-0016's wording, not only direct children), and `issue_states(id, blocked, has_open_children, display_status)`, which is where `waiting` is derived. Later items should read displayed status from `issue_states` and not recompute it in Go.
- Events and comments tables exist with their final columns but nothing writes them yet. `events.old_value`/`new_value` hold JSON text; SQL NULL stands for JSON `null`. Timestamps are RFC 3339 UTC text everywhere; the columns are declared `TEXT`, so the driver scans them as strings, not `time.Time`.
- Tests: 20 (25 with subtests), all against `:memory:` except two on a temp file (WAL check, and two stores writing 150 issues each concurrently, including racing to create the schema). I checked the concurrency test fails with the busy timeout and retry turned off.

### Item 2

- `internal/ids` is pure (stdlib only). `Generate(Seed, nonce, length)` gives `<prefix>-<base36>`: SHA-256 over prefix, title, creator, `created_at` in Unix nanoseconds, and the nonce, taken as a number modulo 36^length and zero-padded. Fields are length-prefixed in the hash input, so `("ab","c")` and `("a","bc")` differ. The description is not hashed (the old tool hashed it; the plan item's list leaves it out).
- `Length(issueCount)`: shortest length from 3 to 8 that keeps the birthday-bound collision probability at or below 25%, the old tool's rule. The steps fall at 164, 984, 5,899, 35,390 and 212,340 issues.
- `Allocate(seed, issueCount, taken)` tries nonces 0–9 at the adaptive length, then at each longer length up to 8, and errors if all are taken. `taken` is a callback, so the package stays pure; item 3's `Create` should call it inside its `Write` transaction with `sqlite.IssueCount` and `sqlite.IssueExists` (the store test `TestAllocatingAnIDInTheCreateTransactionAvoidsATakenID` shows the composition).
- `Resolve(input, []Candidate)`: an exact ID wins and reaches retired issues; otherwise among issues that aren't retired, a unique prefix, then a unique substring. The first tier with any match decides, so two prefix matches are `ambiguous_id` even when a substring match also exists. Errors are `*ids.NotFoundError` and `*ids.AmbiguousError` (sorted `Candidates`, listed in the message), each with `Code()` returning `not_found` / `ambiguous_id`. An empty input is `not_found`.
- A bare hash (`abc` for `t-abc`) resolves through the substring tier; there is no separate "add the prefix" step as in the old tool. Matching is literal and case-sensitive. Imported dotted IDs need nothing special: `bd-abc.1` is an exact match, and `bd-abc` is exact too, so it isn't ambiguous with its old children.
- Store side, in `internal/store/sqlite/ids.go`: `IDCandidates(ctx, tx, input)` (the exact ID by primary key if it exists, else every issue whose ID contains the input via `instr`, retired ones marked), `IssueCount`, `IssueExists`. All read `issues` directly, not `live_issues`, because retired issues keep their IDs and are reachable by exact ID. The store does not import `ids`; `IDCandidate` converts to `ids.Candidate` with a plain type conversion.
- The adaptive length counts every issue, including retired and imported ones with other prefixes. The old tool counted per prefix; counting all is simpler and only ever makes IDs slightly longer.

### Item 3

- `internal/tracker`: `New(store, now, actor)` returns the `Tracker` interface, which so far has `Create(NewIssue)`, `Get(partialID, ...GetOption)` (`WithHistory()` adds `history`) and `Update(partialID, Patch)`. Refusals are `*tracker.Error{Code, Message, Hint}`; the `ids` errors are converted to it, so the CLI has one error type to map. Codes so far: `not_found`, `ambiguous_id`, `invalid_argument`, `retired`.
- `tracker.Issue`, `Links`, `Comment` and `Event` are aliases of the store's types (`internal/store/sqlite/issues.go`, `events.go`), which carry the README's JSON tags in the README's field order. `links`, `comments`, `previous_status` and `history` use `omitzero`: `Get` sets them (empty slices, not nil), `Create`/`Update` leave them nil, so they're absent from those commands' JSON. Item 8 can `json.Marshal` an `Issue` as it is.
- The diff lives in the store: `sqlite.UpdateIssue(ctx, tx, id, sqlite.Patch, at, by)` compares each set field with the row, writes the column and one event per real change, and moves `updated_at` only if something changed (an update that changes nothing leaves `updated_at` alone). `insertEvent` is unexported, so events can only be written from the store. `sqlite.Patch` also has `Status` and `StatusReason`; `tracker.Patch` doesn't. Item 4's `Status` should validate in the tracker and then call `UpdateIssue` with those two fields, so status events come out of the same diff.
- Event IDs are ULIDs made monotonic against the store: `nextEventID` takes a fresh ULID for the event's time, and if it doesn't sort after `max(id)` of `events` it uses that ID plus one. So `ORDER BY id` is the order changes were made in, even with `TESS_NOW` standing still (the acceptance scripts change status twice in one instant and then read `previous_status`). Event values are JSON; they read back as `nil`, `string`, or `int`.
- Timestamps are now written through `sqlite.FormatTime`: RFC 3339 UTC, always with milliseconds (`2026-01-01T00:00:00.000Z`), so text order is time order. Read with `sqlite.ParseTime`. Output goes through `time.Time`'s JSON form, which drops the zero fraction. Anything later that writes a timestamp (status, retire, comments, import) must use `FormatTime`, or `ORDER BY created_at` will misorder mixed widths. `due_at` events log the output form (`2026-02-01T00:00:00Z`).
- `Create` logs no events, including for the parent and blocked-by links it creates (ADR-0013: "creation logs nothing"). `InsertIssue` writes those link rows itself. A retired parent or blocker is refused with `retired`; a partial ID works for both. Assignee `""` means none. Titles are kept verbatim; a blank one is `invalid_argument`. Types are `tracker.IssueTypes`; a label that is empty or only whitespace is `invalid_argument`.
- `previous_status` is the old value of the issue's latest `status` event, and only when that event's new value is `held`; a held issue with no such event (an import) has none. `parent` and `ancestors` come from `issue_ancestors`, so a retired parent is left out, the same way `links.*` leave retired issues out, and a retired issue itself reads with no parent.
- Tests: 21 in `internal/tracker/tracker_test.go`, all through the interface on `:memory:`. Three things this item's interface can't do yet are set up from the test with the store directly: retiring (raw `UPDATE`), status changes (`sqlite.UpdateIssue` with `Status`), and `related`/`discovered-from` links and comments (raw `INSERT`). Items 4–6 should swap those helpers for the real methods.

### Reflections

One `- Item N:` bullet group per iteration. Where the docs or suite were ambiguous or felt wrong and how it was resolved, anything done without confidence, and friction with the prompt, plan, sandbox, or checks. The human reads these to decide what to look at later.

- Item 1:
  - `readiness_edges` leaves out links that touch a retired issue, as ADR-0010 asks for readiness. ADR-0007 also has cycle detection query it. That leaves a gap item 5 should decide on: with `X blocks R blocks Y` and R retired, `Y blocks X` passes a cycle check over the view, and restoring R then closes a loop. Checking cycles over `links` directly (retired included) would close it; the views' depth guard keeps a loop from hanging either way.
  - A `done` issue with an active blocker, and a `done` child of a held parent, are in `blocked_issues`. That follows the definition literally ("any issue can be blocked"), but `list --blocked --all` would show them; nothing in the suite covers it.
  - The item asked for "a view or query for has open children"; I also added `issue_states` so the `waiting` derivation lives in SQL next to `blocked_issues`. That is slightly beyond the item's list. I did not benchmark the views at 10K issues; the ADR-0007 numbers are from the spike's schema, not this one.
  - The prompt asks for the store tests "against `:memory:`", but two connections can't share a `:memory:` database, so the concurrency and WAL tests use a file under `t.TempDir()`. The `tdd` skill wants seams confirmed with the user first; unattended, I took the seam the plan item names.
  - `Write` hands callers a raw `*sql.Tx`. ADR-0013 says only the store writes events, so items 3+ should add store functions that take the tx (as `SetConfig` does) instead of writing SQL in `tracker`.
- Item 2:
  - The docs say "exact, then prefix, then unique substring" and the suite resolves a bare hash (`slice AHASH $A 2`). I kept the three tiers literal, so with `t-abc` and `t-abcd` both live the bare `abc` is ambiguous and the user has to type `t-abc`. The old tool preferred an exact hash-part match in that case. Adding that as a tier is a few lines in `Resolve` if it's wanted; I left it out because the docs don't name it.
  - The module map says "Lookup is an indexed store query" and the hand-off asks for the substring step to be indexed. Only the exact step is (primary key); a partial ID scans the primary-key b-tree with `instr`. A real substring index would need a trigram or FTS table, which seemed out of proportion at 10K issues. Not benchmarked.
  - "Collision handling inside the create transaction" can't be fully landed before `Create` exists (item 3). What's here is the pure `Allocate` plus the store lookups and a store test that runs them in one `Write` transaction. Item 3 still has to wire it.
  - For the resolution rules I wrote the tests and the implementation in one step and didn't watch each test fail first; generation and the store functions did go red then green.
- Item 3:
  - The module map's draft has `Get(ctx, partialID)`; I added variadic options for "history on request" instead of a second method. The draft's `Close` is superseded by ADR-0018's `Status` (item 4), and the draft's `Comment(id, author, text)` takes an author where the plan says it comes from the actor.
  - Putting JSON tags on store types, and aliasing them as the tracker's, blurs "cli owns the JSON shapes" from the module map. I chose it over three copies of a 21-field struct. If the human wants the shape owned by `cli`, it's a mechanical change in item 8.
  - `GetIssue` joins `issue_states` for one ID, which evaluates the recursive `blocked_issues` view; and it runs two more queries for labels and ancestors. Fine for `show`; item 6's `List` shouldn't call it per row. Not benchmarked.
  - TDD was not one test at a time: I wrote the whole test file first (red: no package), then the implementation, and it went green in one step. To check the tests weren't passing by construction I broke the monotonic event ID step and saw six tests fail; a second mutation (dropping the "only if changed" guards) didn't compile, so I didn't see that one fail. The fixed-millisecond timestamp format is my own call; no doc asks for it.
