# Loop 2 plan: sync

The ordered work list for the second build loop ([build plan](../../docs/design/build-plan.md), [sync.md](../../docs/design/sync.md)). One item per iteration, in order; the loop checks items off and the host stops when every item is checked and `scripts/ralph/check.sh --strict` passes. Each item names the docs that define it and what "done" means. The docs are the spec; this file only orders the work. Loop 1's plan and notes are in [plan-loop1.md](plan-loop1.md).

Package layout, from [module-map.md](../../docs/design/module-map.md): `internal/git` (runs the git binary), `internal/sync` (snapshot, merge, store, `Run`; the exported API in `sync.go` is fixed by [acceptance/README.md](../../acceptance/README.md) "The simulator"), `internal/sync/gitref` (the transport, the only place that knows ref names), and `internal/cli` for `sync`, `doctor` and the hooks.

## Notes

Iterations append here, newest at the bottom, under a heading `### Item N`. Human-facing: decisions, deviations, gotchas, what to look at by hand.

### Item 1

- `internal/git` is `git.Repo{Dir}` (empty `Dir` is the working directory) with one method per operation, each one git process: `CommonDir`, `WorktreeRoot`, `ResolveRef`, `Remotes`, `UpdateRef` (git.go); `WriteCommit`, `ListTree`, `ReadBlobs`, and the in-process `BlobHash` (objects.go); `Fetch`, `Push` (remote.go). The package knows no ref names; every ref is an argument.
- Writing is `fast-import`, one process for blobs, trees and the commit. fast-import insists on a branch name for a commit and would write that ref at the end, so the stream names a scratch branch (`refs/fast-import/scratch`), then `reset`s it with no commit, which leaves fast-import nothing to write; the commit's ID comes back through `get-mark`. A test asserts no ref exists afterwards. `--done` makes a truncated stream an error.
- `Commit.Files` and `Commit.Delete` are changes against the first parent's tree (fast-import's `from` semantics; empty tree with no parents). Item 6 should put the commit it diffs against first in `Parents` and send only the files whose `BlobHash` differs from `ListTree` of that parent.
- Identity and dates are written into the stream from `Signature{Name, Email, When}`, always `+0000`; a test sets every `GIT_AUTHOR_*`/`GIT_COMMITTER_*` variable and checks none reaches the commit. `<`, `>` and newlines are dropped from a name, as git drops them.
- Push classification reads `push --porcelain`: a `!` line for the ref with `[rejected] (stale info | fetch first | non-fast-forward)` is `git.ErrRemoteMoved` (a sentinel, not a `*tracker.Error`: the transport retries and decides when it becomes `push_rejected`); any other `!` line is `push_rejected` carrying git's reason plus the remote's `remote:` lines; a failed push with no `!` line is `offline`. With `--force-with-lease` a moved remote reads `stale info`, not `non-fast-forward`; that is the case the test covers.
- `Fetch` returns `(found, err)`: a remote without the ref is `false, nil` (read from git's "couldn't find remote ref", which is why every git process runs with `LC_ALL=C`) and leaves the destination ref as it was; any other failure is `offline` with git's first `fatal:` line in the message. A context that ended comes back as the context's error, not `offline`, so item 10's deadline can be told apart.
- `Push` passes `--no-verify`, so the user's own `pre-push` hook (their test run, say) doesn't fire on a sync, and `--no-follow-tags`/`--no-recurse-submodules`; `Fetch` passes `--no-tags --no-write-fetch-head --no-recurse-submodules`. None of this is in sync.md; say if any of it should not be there.
- `cli/env.go` now calls `git.Repo{}.CommonDir` and `WorktreeRoot`; `not_a_git_repo` is `git.CodeNotAGitRepo`, and the "not inside a working tree" case is `git.ErrNoWorktree`, mapped to `invalid_argument` in `cli` as before. No deviations from the docs.

### Item 2

- `internal/sync/snapshot.go` holds `Files()` and `FromFiles(files map[string][]byte) (*Snapshot, error)`; `internal/sync/load.go` holds `Load`. The key order is the declaration order of four unexported file structs (`configFile`, `issueFile`, `commentFile`, `eventFile`) written with `encoding/json`, HTML escaping off, so `<`, `>` and `&` appear as themselves. New exported names beside the fixed API: `FromFiles`, `Format` (1) and `CodeFormatUnsupported`.
- `Files()` sorts copies of the collections and never changes the snapshot; a nil collection is written `[]`. It writes `related` as the snapshot holds it: putting it on the smaller ID is done by whoever builds the snapshot (`Load` here, `Merge` in item 3).
- `FromFiles` is strict: a path outside the five kinds, a key it does not know, a second JSON value in a file, an ID or issue ID that does not match the path, or a text whose bytes do not hash to its name is an error. Rewriting a snapshot would silently lose anything it skipped. It reads only `format` from `config.json` first and returns `format_unsupported` (a `*tracker.Error`, hint to upgrade) before parsing anything else, so a later format is free to reshape every file. The other failures are plain errors with no stable code.
- `Load` reads the `issues`, `labels`, `links`, `comments`, `events` and `texts` tables directly, in one read transaction, not through `live_issues` or `issue_states`: the stored status, retired issues, and links to and from retired issues (a child keeps its `parent` in the snapshot while the tracker shows none because the parent is retired). Which issue holds a link comes from `sqlite.LinkOwner`, the function the store logs link events with, after turning a `related` row so the smaller ID is first.
- Timestamps are cut (not rounded) to the second in `Load` and in `FromFiles`, so a snapshot in memory equals its files. The database keeps milliseconds.
- Event values are the plain JSON values in both `Load` and `FromFiles`: `nil`, `string`, `float64` (a priority event is `float64(1)`, not `int`), matching what the README says of `Resolution.Kept`/`Dropped`.
- `Load` of a missing or uninitialised database is `not_initialized` and creates no file, as `tracker.Open` does. The message is a copy of the tracker's, whose constructor is unexported.
- No deviations from the docs.

### Item 3

- `internal/sync/merge.go` holds `Merge`. New exported names beside the fixed API: `CodeConflict`, `CodePrefixMismatch`, `WonLocal`, `WonRemote`, `ReasonLater`, `ReasonRetired` (item 4 adds its own reason for `cycle`). The returned resolutions are never nil, and are ordered by issue ID, then the scalar units in sync.md's order, then `labels`, `blocked_by`, `discovered_from` by element, then `related`.
- Every unit on which the sides differ becomes a `choice` (each side's value and latest new event), decided by one function, `decide`, for scalars, collection elements and related pairs alike; the retire rule (`retirement.refuse`) and the reporting (`settle`) run over the same choices. Item 4 can add its link dropping after `m.related(out)` in `Merge` and append to `m.resolved` before the final sort.
- New events are indexed once per side (`newEvents`: events whose ID the LKG lacks, the latest per attr, and per attr and element for collections, an add found by its new value and a removal by its old), so the merge is linear in events, not events times units.
- `related` is merged in its own pass after the issues, per pair: the pair lives on the smaller ID whichever issue an input lists it on, its events are read from both endpoints, and its resolution names the smaller ID as `Issue` and the other as the element. Its fallback `updated_at` is the smaller-ID issue's.
- A collection resolution's `Kept`/`Dropped` are each side's value for the element: the element where the side has it, `nil` where it does not. So a removal that wins is `Kept: nil, Dropped: "ui"`, and a removal the retire rule refuses is `Kept: "ui", Dropped: nil`.
- An ID collision resolved by the retired-record exception records the kept side; events and comments under that ID that the kept side does not hold are left out of the union. Item 5 has to delete those rows from the copy that held the dropped record, which sync.md's "rows the merged snapshot does not mention are left alone" does not cover: the write needs to know the issue was replaced whole (the merged record's `created_at`/`created_by` differ from the database's).
- A non-nil snapshot must have `Config.Format == Format` or the merge fails with `format_unsupported`; an absent LKG or remote ref must be passed as `nil`, not as `&Snapshot{}`. `prefix_mismatch` compares ours and theirs only.
- The same latest event on both sides (a copy that lost its LKG, or a retry after a failed database write) decides nothing: the unit falls through to the no-event fallbacks and is not reported. No deviations from the docs.

### Item 4

- `internal/sync/structure.go` holds the pass, `m.structure(out)`, which `Merge` runs after the issues and `related` are merged and before the events are gathered. New exported name: `ReasonCycle`. A drop is `Resolution{Issue: the issue holding the link, Field: "blocked_by" or "parent", Kept: nil, Dropped: the other issue, Reason: "cycle"}`; drops come after an issue's field resolutions, in the order they were made.
- Each round, `violations` returns every `parent` and `blocks` link that takes part in any breach: links between two issues of one strongly connected component of the "held up by" graph (issue → its parent and its blockers; Tarjan, so a round is linear in issues and links), a link to itself, and for a `blocks` link from an ancestor to a descendant, that link plus the parent links between the two. A descendant blocking its ancestor has no code of its own: with the parent links between them it is a loop.
- Of those links, the ones the LKG's record of the issue lacks are the candidates, and the latest is dropped: one link per round, the latest over all breaches at once and not per breach. That link is also the latest candidate of every breach it is in, so it is what ADR-0022 asks for, and the result does not depend on the order breaches are found in.
- A link's time is the latest new event of its unit (`parent`; the `blocked_by` element) on the sides whose record has the link. With no event anywhere: the later `updated_at` of the issue holding the link in the merged result, then the larger (issue, field, other), the same shape as the field merge's fallbacks.
- `Won` names the side that did not make the dropped link. When both sides made it, the side with the later event is the one overruled.
- Retired issues are in the check like any other; nothing in the pass reads `retired_at`.
- No deviations from the docs. One addition they don't cover: if a breach has no new link at all (only possible when the LKG itself breaks the rules, so a hand-written one), every link in it is a candidate, so the result is still clean and the loop ends.

### Item 5

- `internal/sync/store.go` holds `Store(ctx, dbPath, ours, merged, at)`, the name the module map gives. It takes `ours`, the snapshot the merge was given, as well as the merged one: "every issue it changed" is the issues whose merged record differs from ours (compared as their canonical files). Nothing was needed in `internal/store/sqlite`; like `Load`, the write holds its own SQL over the tables, inside `sqlite.Store.Write`, which is the `BEGIN IMMEDIATE` transaction. New exported names: `Store`, `RecordFailure`, `ErrChangedDuringSync`, `ConfigLastAt`, `ConfigLastResult`, `ResultOK`.
- The transaction first reads the database as a snapshot. For a changed issue the row is updated in place (or inserted), and its labels and the links it holds are diffed against the stored ones: only rows that went are deleted and only new ones inserted, so a link or label in both is not touched. Comments, events and texts are added when the database lacks the ID or hash, for every issue, changed or not (a comment moves no `updated_at`).
- Deviation from the letter of sync.md, on purpose: a command can run between `Load` and the write (the fetch and push take seconds; only syncs are serialised by the lock). An issue the merge did not change is not written, so such a command's work on it stays, with its events. If the command changed an issue the merge also changed, `Store` writes nothing and returns `ErrChangedDuringSync` naming the issue; the local ref has not moved, so the next sync merges the same remote state with the edit. Item 6 decides what `Run` does with it (merge again at once, or fail). Writing over it would leave a row that disagrees with its own latest event.
- Timestamps: a snapshot is to the second, the database to the millisecond. An updated row keeps the stored text of `created_at`, `updated_at`, `due_at` and `retired_at` wherever the merged value is the same second, so the copy that made an issue keeps its `list` order. New rows, comments and events are written with `.000`.
- The retired-record exception of ADR-0023 (note of item 3): an issue whose stored `created_at` or `created_by` differs from the merged record's was replaced whole, and its comments and events that the merged snapshot lacks are deleted. That is the only delete of a record the write does. Texts are never deleted.
- `sync.last_at` is written as RFC 3339 UTC to the second, with `sync.last_result` `ok`, in the same transaction. `RecordFailure(ctx, dbPath, code)` sets only `sync.last_result`, so `sync.last_at` stays the time of the last sync that worked; nothing calls it yet.
- `Store` and `RecordFailure` refuse a missing or uninitialised database with `not_initialized` and create no file. `Files()` now builds an issue's file through `issueBytes`, which the write uses to compare records.

### Item 6

- The code was written by the iteration that aborted on the simulator harness and committed by the host as work in progress (`2f1567e`). This iteration read it against sync.md and the README, ran the scenarios (21 of 21 pass, and the 5 short random runs), added one unit test, and ran ten one-line mutations of `run.go` and `gitref.go`, all of which a unit test catches.
- `internal/sync/gitref` is `Transport` (`Open`, `Remote`, `Local`, `Fetch`, `Push`, `Advance`) over `Tree{Commit, Files}`; the zero `Tree` is a ref that does not exist. It holds the only copies of `refs/tess/sync` and `refs/tess/remotes/<remote>/sync`, deals in path-to-bytes trees, and knows nothing of snapshots. A blob is read once per transport, so the retry and the LKG/theirs overlap cost no second `cat-file`.
- `Push` writes one `fast-import` commit against the LKG's tree (theirs' when there is no LKG), sending only files whose blob hash differs, with parents LKG then theirs (one parent when they are the same commit or one is absent), then pushes with the lease at the fetched commit. It moves nothing local. When the remote already holds exactly the merged tree, `Run` pushes nothing and advances the local ref to the remote's commit, so "up to date" makes no commit.
- `Run` (run.go) takes the lock, then up to three rounds of `Load`, `Local`, `Fetch`, `Merge`, `Push`; then `Store`, then `Advance`. `ErrRemoteMoved` starts the next round; the third is `push_rejected`. `ErrChangedDuringSync` from `Store` (item 5) also starts the next round, and after three is `busy`: the push has landed by then, the local ref has not moved, and the next sync merges the same remote state.
- The lock is `<database>.sync.lock`, an exclusive `flock` polled every 50 ms for 30 seconds (lock_unix.go), so a killed sync leaves nothing locked; the file stays. Elsewhere (lock_other.go) it is create-exclusive and a killed sync leaves a file to remove by hand. The lock is taken after the remote is chosen, so `no_remote` and `not_initialized` create no lock file. A context that ends while waiting is the context's error, not `busy`.
- A failed sync calls `RecordFailure`, so `sync.last_result` holds the code and `sync.last_at` stays; not for `--dry-run`, not for `not_initialized`, not when the context ended, and not for an error without a code.
- `Fetched` is the issues whose files (the issue, its comments, its events) differ between ours and the merged tree; `Pushed` the same between theirs and the merged tree. `(*Result).Summary()` is new and exported: the README's one line, which is also the commit message after `tess sync: `. Item 7 can print it. Other new exported names: `CodeNoRemote`, `CodeOffline`, `CodePushRejected`, `CodeBusy`.
- No deviations from the docs beyond item 5's `ErrChangedDuringSync`, which this item turns into a retry.

### Discovered

(Work found outside the current item: one line each, for the human to turn into items or issues.)

- `cli/env.go` `actor` still runs `git config user.name` itself; item 1 moved only the `rev-parse` helpers it named. It could become `git.Repo.UserName` so `internal/git` is the only place that starts git.
- `internal/git` assumes SHA-1 object IDs in `BlobHash` (sync.md says SHA-1). A repository created with `--object-format=sha256` would see every blob as changed; `tess doctor` could say so.
- `internal/sync` repeats the `not_initialized` error text of `tracker/open.go` in `load.go`; exporting the tracker's constructor would leave one copy.
- Locked suite, for the human to look at before item 6 (found by reading, not by running: `Run` does not exist yet). `acceptance/sim/invariants_test.go` `checkLatestEventWins` checks `status` and `status_reason` as two scalars, each against its own latest event, while sync.md merges them as one unit. In the scenario "status and reason travel together" copy a logs `status_reason: null → "waiting on something"`, copy b's `done` logs no `status_reason` event, the scenario itself expects `status_reason null`, and the invariant then appears to want `"waiting on something"`. The same seems true of any random run where a held or omit loses to a status with no reason.
- Locked suite, same caveat. The scenario "retire on one copy, restore on the other, later wins" ends with `expect b X retired_at null`, but b's retire is the latest `retired_at` event in the script (a restores, then b restores and retires), so the latest-event rule and `checkLatestEventWins` both appear to want X retired on b.
- Locked suite, same caveat. `checkLatestEventWins` excuses a collection element only by `r.Dropped`. When the retire rule refuses a removal made after the retire (a label or blocker removed on the other copy), the element stays, and the resolution is `Kept: element, Dropped: nil` by the README's wording, so the invariant looks up `labels/null` and appears to fail on "snapshot has X, which the latest event removed". Item 8 will meet this in random runs if it is real.
- `Resolution` has no times, but the plain output of `tess sync` prints each side's event time (`kept "From b" (other copy, 2026-01-03T00:00:00Z)`) and the retire's time. The struct is fixed by the README, so item 7 needs another way to get them (the merged snapshot's events are not in `Result` either).

### Reflections

(Candid notes on the docs, the suite, and the process, per item.)

- Item 1: a failed push or fetch that never reached a per-ref answer is reported as `offline`, whatever the cause. That is right for an unreachable remote and for failed authentication, but a local failure (a corrupt object, a full disk) would read as `offline` too. Git's own first `fatal:` line is in the message, so the user sees the real reason; I did not try to tell these apart by matching more of git's wording.
- Item 1: I also treat a `[remote rejected]` whose reason starts `failed to update ref` or `failed to lock` as `ErrRemoteMoved`: it is what the remote says when another push lands between its advertisement and our update. I could not produce that race in a test, so that branch is untested; if the reason is really a permanent one (permissions on the remote's ref), the cost is two wasted retries before `push_rejected`.
- Item 1: the item says "a non-fast-forward push after the remote moved", but with `--force-with-lease` git never reports `non-fast-forward` for this; it reports `stale info`. I took the item to mean the situation, not the word, and accept all three of git's wordings.
- Item 1: git prompts are left alone (no `GIT_TERMINAL_PROMPT=0`). A remote that asks for a password would hang the session-start hook until its ten-second deadline; item 10 may want prompts off for the hook only.
- Item 2: item 5 should know that the snapshot is to the second and the database to the millisecond. Writing a merged issue back replaces `updated_at`, `created_at` and event `changed_at` with whole seconds; that is harmless for the merge (event order falls back to the event ID, a ULID that keeps its milliseconds), but a row the sync rewrites loses its milliseconds, and `list` orders by `created_at`. Item 5 could keep the stored value where the second matches.
- Item 2: "two databases that reach the same state by different operation orders give identical files" cannot hold for the whole tree once an operation logs an event or a comment, since those IDs are random ULIDs. I tested it in two parts: a creation-only build in two orders (labels and blockers given in different orders) compared file for file, and edits in different orders at one clock time compared on everything but `events/`.
- Item 2: a `related` link given in opposite wordings gives the same `related` list but not the same issue files: the tracker logs the link, and moves `updated_at`, on the issue it was given from, so the two copies differ in `updated_at` on both endpoints until a merge takes the later one. sync.md's "produce the same file" is true of the link, not of the whole file. My first version of the test asserted the whole file and failed on this; the test now uses one wording there and a separate test covers the opposite wordings.
- Item 2: strictness in `FromFiles` is my call, not the docs'. The cost is that a stray file on the ref (someone commits a README to `refs/tess/sync` by hand) fails every sync with an uncoded error until it is removed. If a later item wants that to be a code, `doctor` or `Run` is the place.
- Item 3: "a resolution is reported when both sides have a new event for the unit" is taken literally, so after a lost LKG a unit is reported whenever both copies hold any event for it, including an event one copy got from the other. A copy that fetched `title → A` and then set `title → B` reports a resolution against the copy that only ever had `A`. It picks the right value; the report is noise. I did not narrow it to "each side has an event the other lacks" because the docs don't say that.
- Item 3: the retire rule is applied to a `related` pair only through the issue that holds it (the smaller ID), and not at all to links held on another issue that point at the retired one (`blocked_by` on a dependent, `parent` on a child). sync.md says "every unit" of the retired issue; whether a link made to an issue after it was retired elsewhere should stand is not said. A single copy would have refused it.
- Item 3: with no LKG record, "the side that differs from the LKG" compares against an empty issue (sync.md: "merged with an empty LKG record"). For scalars that almost never separates the sides and the later `updated_at` decides; for a collection element the side that has it always wins, so two copies that imported the same file and then diverged without events keep the union of their labels and links.
- Item 3: when the retire has no event (an imported tombstone), the retire's time is `retired_at` itself with an empty event ID, so an edit in that same second counts as after it. Untested beyond the reasoning; it needs a hand-written or imported snapshot to happen.
- Item 3: I wrote the tests for "which issues" and config first and watched them fail, then the whole merge, then the tests for the remaining rules, which passed on first run. To check they were not vacuous I ran fourteen one-line mutations of `merge.go` (no retire rule, the three-way shortcut, each tie-break inverted or removed, LKG events counted as new, and so on); two survived and got a test each, and all fourteen now fail at least one test.
- Item 4: the copy that made a dropped link drops it again on its own next sync, and reports it again. Its record still has the link and the incoming snapshot has the link's add event too, so both sides hold the same latest event, the unit falls to "the only side that differs from the LKG", the link comes back, and the structure pass removes it a second time. The end state is right and both copies hear of the drop (which the scenario "blocks links that close a loop across copies" seems to want, since it does not say which copy), but it rests on two rules lining up, not on anything written down. Item 8 should watch for it with three copies.
- Item 4: when both sides hold a dropped link by the same event, or by none, nothing tells the sides apart and `Won` is `local` whichever way round the merge runs, so "the same resolutions with `won` flipped" does not hold for that one case. I could only build it with a hand-written LKG that already had a loop; that test calls `Merge` directly and compares the files only.
- Item 4: a unit can now be reported twice in one merge: a `parent` that two copies set differently gets `later`, and if the winner then closes a loop, `cycle` as well. The README does not say whether that should be one line; I left both.
- Item 4: I wrote the first test, watched it fail, wrote the pass, then the other tests, most of which passed at once. To check them I ran thirteen one-line mutations of `structure.go`; seven survived the first time. One showed dead code (the separate descendant-blocks-ancestor check, removed), the others got four tests and one corrected test, and all are now caught.
- Item 5: sync.md says `sync.last_result` is "`ok`, or the error code", which reads as if a failed sync writes it, while "a failed sync changes nothing in the database" and the README's `Last sync: <when>, not synced now (<code>)` need the time of the last good sync to survive a failure. I split it: `Store` writes both on success, `RecordFailure` writes only the result. Whether a failed sync should write the config at all (it is a database write, though not to issues) is for item 6 or the human; the hook runs the sync in-process and may not need the stored code.
- Item 5: `ErrChangedDuringSync` is my addition; the docs do not consider a command running during a sync. The check compares the whole record of each changed issue, so a concurrent edit to a different field of the same issue also refuses the write. That is stricter than needed but never loses an edit. A link a concurrent command makes on an unchanged issue is not checked against the links the merge wrote, so the two could in principle close a loop that neither the store nor the merge saw; the next sync's structure pass would see it only if one of the links is new since the LKG.
- Item 5: the write trusts the merged snapshot. It does not check that a text's body hashes to its name or that the structure rules hold; foreign keys and the unique indexes are the only guard, and a breach rolls the whole write back with a plain error. `related` is expected on the smaller ID, as `Merge` gives it; a hand-built snapshot listing a pair on both issues would fail on the unique index.
- Item 5: the write reads the whole database again inside the transaction to diff against, so a sync loads the database twice. Fine at the sizes tested; if it shows at ten thousand issues, the read can be narrowed to the changed issues and an existence check on IDs.
- Item 5: most tests passed on the first run of the implementation, so I ran sixteen one-line mutations of `store.go`. Three survived the first time: two got a test (milliseconds of `updated_at` and `due_at`), and one showed that ordering every delete before every insert across issues bought nothing, since a parent link's uniqueness is per child; the code now orders them within an issue only, and that order is covered by a test.
- Item 6: I did not write this code; I reviewed it. I did not use the `tdd` skill, since there was nothing left to write test-first: the one test I added (a pushed sync whose database write keeps failing leaves the local ref at the LKG and converges on the next sync) passed at once, and I checked it by mutation instead (moving the ref before the write fails it).
- Item 6: `busy` for "a command kept changing an issue the merge changed, three times" is a stretch of the code's meaning (sync.md: another sync holds the lock). It is the closest code, and the hint is the same: run it again. In that case the remote already has this copy's merged commit while the copy does not, which is the state sync.md's "order of 4 and 5" paragraph describes as safe.
- Item 6: the commit message is `tess sync: fetched N issues, pushed N` with the counts of the round that pushed. sync.md says "`tess sync` plus the summary line" without giving the joiner; the colon is the earlier iteration's reading.
- Item 6: `Run` reads the whole fetched tree and the whole LKG tree on every sync (two `ls-tree`, one or two `cat-file --batch`), and `Load`s the database once per round and again inside `Store`. Not measured at ten thousand issues. `Resolution` still lacks `KeptAt`/`DroppedAt`; the plan gives them to item 7 and the simulator compiles without them.
